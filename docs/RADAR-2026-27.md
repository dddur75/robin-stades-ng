# Radar papier 2026-27 — décision le 17 novembre 2026

Le radar mesure rétrospectivement les prix français contre le fair Pinnacle de
clôture du moteur `src/robin/clv.py`, inchangé. Aucun pari, achat, nouvel abonnement,
appel fournisseur ou accès Neon/R2. Les fichiers de collecte, configurations
existantes, budgets et verrous sont inchangés. L'unique workflow ajouté lit des
artefacts GitHub déjà produits et publie des résultats comme artefact Actions,
sans commit automatique, sans promotion et sans déclencher la collecte.

## Reproduction

```sh
PYTHONPATH=src python scripts/radar_hebdo.py --through 2026-10-19
# Depuis les rapports normalisés locaux, avec les fenêtres et exclusions du CLV :
PYTHONPATH=src python scripts/radar_hebdo.py --stock /chemin/stock --through 2026-11-16
# Import manuel optionnel :
PYTHONPATH=src python scripts/radar_hebdo.py --boosts data/radar/boosts.csv --through 2026-10-19
```

Dépendances Python : pydantic, scipy et requests (import du parseur existant,
aucune requête). Les chemins sont relatifs à la racine du dépôt. Les exports sont
`reports/radar/2026-27/SEMAINE-AAAA-WW.md`, `RADAR.md`, `DETAIL-HORIZONS.csv`,
`PREMIERS-FRANCHISSEMENTS.csv`, `BOOSTS.csv` et `SOURCES.json` (hashes des entrées).
Les agrégations sont par semaine ISO du coup d'envoi UTC, book et bande de fair
(<30 %, 30–45 %, 45–60 %, ≥60 %). Les premières apparitions sont ventilées par
horizon ; les répétitions par horizon figurent dans une table distincte.

Une seule sélection `(match, issue, book)` par seuil, même si elle apparaît à
T−48, T−24 et T−2 ou en boost : le prix et le gain sont ceux du premier
franchissement de ce seuil. Exemple : EV +0,5 % à T−48, +2 % à T−24, +5 % à T−2
= **1 / 1 / 1**, apparitions **48 / 24 / 2**. Les trois compteurs se recouvrent.
EV+ est strictement positive : la mention « ≥0 » n'inclut pas les EV nulles.
Les seuils 2 % et 5 % sont inclusifs, tolérance numérique 1e−12.
Chaque colonne de gain représente la somme de 10 € × EV aux premiers prix de
son seuil. C'est un gain attendu brut théorique, sans résultats réalisés,
indépendance statistique ni preuve d'avantage exploitable.

La borne par défaut est hier à Paris, plafonnée au 16 novembre inclus, pour la
décision du 17. Les semaines sans match dans les entrées sont affichées avec
zéro opportunité **observée**, jamais présentées comme couvertes. La dernière
journée disponible et la borne demandée restent visibles, y compris si le stock
est ancien. Un match avec horaires contradictoires reste exclu par le CLV.

## Import manuel

`data/radar/boosts.csv` est un fichier d'entrée, vide à la livraison :

```csv
date,book,match,issue,cote_boostee,mise_max
```

- `date` : instant **réel de consultation**, ISO 8601 en UTC avec `Z` ou `+00:00` ;
  strictement antérieur au coup d'envoi. Pas une simple date sans heure.
- `book` : `betclic_fr`, `winamax_fr`, `unibet_fr`, `pmu_fr`, `netbet_fr`.
- `match` : identifiant canonique de `DETAIL-HORIZONS.csv`, pas un nom rapproché
  approximativement. Le fair et le coup d'envoi doivent être connus et cohérents.
- `issue` : `1`, `N`, `2`, exclusivement un simple résultat temps réglementaire
  1N2, même périmètre que Pinnacle. Pas de combiné, buteur, handicap ni qualification.
- `cote_boostee` et `mise_max` : décimaux avec point, finis, cote >1, mise max >0.
  Saisir seulement une offre ferme dont David connaît les conditions, accessible
  au compte et sans exigence de pari préalable, freebet ou rollover. Aucun pari.

Un boost à 2,40 pour p juste = 0,50 donne EV = +20 % et gain à 10 € = 2 €.
Si mise max = 5 €, le gain fixe est **non éligible**, `gain_10_eligible=false`,
`gain_capped=1 €`. Aucune mise n'est envoyée. Les doublons identiques n'ajoutent
rien ; contradictions de prix au même instant, fair incohérent, référence
manquante ou prix au/après coup d'envoi font échouer l'import explicitement.

## Exécution hebdomadaire

`radar-hebdo.yml` : `workflow_dispatch` et lundi 07:17 UTC (08:17 à Paris les
26/10, 02/11, 09/11 et 16/11). Le contrôle de date rend le job inactif après le
17/11 ; un dispatch le 17 permet le bilan final jusqu'au 16 inclus.
Droits : `contents: read`, `actions: read`, aucun secret fournisseur/Neon/R2.
Le script de calcul est local ; seul le workflow récupère les rapports déjà
collectés sur GitHub. Il ne déclenche aucun workflow de collecte. Les installations
Python et le temps Actions utilisent l'infrastructure existante ; pas de garantie
sur un éventuel quota Actions propre au compte, aucun plafond modifié.
Le workflow utilise `--baseline reports/clv/2026-27` : les journées initiales
jusqu'au 19/10 sont figées et hachées ; seules les journées suivantes sont
recalculées depuis le stock. Le socle ne disparaît donc pas à l'expiration des
archives. Aucun résultat initial n'est réécrit. Une identité de match traversant
cette frontière fait échouer le calcul. Les journées futures restent limitées
par le stock disponible, sans garantie d'exhaustivité.
Les nouveaux rapports restent en artefact Actions (35 jours) et résumé de run,
à consulter ou intégrer par revue ; le workflow ne peut pas modifier Git.

La rétention GitHub peut tronquer le stock : conserver les entrées normalisées
hors Git pour reproduire ; ne jamais annoncer une couverture exhaustive R2.
Un téléchargement refusé fait échouer le job ; les résultats versionnés ne sont
pas réannoncés comme frais. Le nouveau workflow devra être fusionné par le
processus habituel avant que son cron s'applique ; aucun dispatch exécuté ici.
